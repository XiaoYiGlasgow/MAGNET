# Official nuPlan closed-loop evaluation harness (rebuilt version)

> Created: 2026-07-28. Belongs to: VT-2026-04191 MAGNET resubmission, rebuild of the closed-loop evaluation pipeline for Stages ⑤/⑧.

## Why it was rebuilt

The closed-loop harness for Stages ⑤/⑧ was kept entirely under the session-level `scratchpad/` and has now been lost:

| Lost asset | Original purpose |
|---|---|
| `eval_matrix.sh` / `eval_gnn_pgh.sh` / `eval_baselines_pgh.sh` | Driver for the 3 planner × 2 mode matrix |
| `gpu_watcher.sh` (v3 Bark) | Automatic trigger when an exclusive GPU becomes available |
| `extract_scores.py` / `bark_summary.py` | Score extraction from the aggregator parquet |
| `boston_clean/` (300 symlinks), `pittsburgh_clean/` (300 symlinks) | Deep-screened evaluation DB subsets |
| `eval_full/`, `eval_full_pgh/` | All raw simulation outputs |
| `step0_heldout_pgh.py` / `pittsburgh_validate.py` | Held-out pool construction and deep screening |

**Consequence**: Boston-250's `0.122/0.095` and the Stage ⑧ Pittsburgh baselines `IDM 0.591/0.564`,
`LogFuture 0.815/0.543` currently **exist only as stage-record text, with no reproducible artefacts**. This is a substantive gap in D0 provenance
(Stage 15 §3.1 #5): these numbers may be cited in the resubmission, but **cannot be claimed as reproducible**
unless they are re-run with the harness in this directory.

This directory is the auditable rebuilt version, kept under a version-tracked path rather than in `scratchpad/`.

## Files

| File | Purpose |
|---|---|
| `build_pittsburgh_heldout.py` | Rebuilds the Stage ⑧ in-dist evaluation pool: `train_pittsburgh` 1560 DBs − 600 logs used by E1 = 960 held-out (with a hard zero-overlap assertion); 300 clean are taken after deep screening |
| `run_closed_loop.sh` | Hydra call for a single (scenario set × planner × mode), all absolute paths; each run writes a provenance JSON |
| `extract_scores.py` | Reads `aggregator_metric/*weighted_average*.parquet` → final score + 6 sub-metrics + breakdown by `scenario_type` |
| `queue_pittsburgh_indist.sh` | GPU queue scheduler: polls the three GPUs; the first one that is nearly exclusive 3 times in a row (used < 4000 MiB) runs the whole batch of 6 cells, then automatically extracts scores and sends a Bark notification |
| `logs_pittsburgh_heldout.txt` | 960 held-out log names (generated by `--build`) |
| `logs_pittsburgh_heldout_clean.txt` | 300 log names that passed deep screening (generated by `--validate`) |
| `logs_pittsburgh_{val,test}60.txt` | split3 val/test log names, **not used by the current closed loop**; see "Scenario set selection" below |

## Scenario set selection (important)

| Scenario set | Definition | Use |
|---|---|---|
| `pittsburgh_heldout` ✅ **currently used** | 300 clean DBs from the 960 held-out after deep screening, **zero overlap with E1's 600 logs** | In-dist closed-loop comparison, following the Stage ⑧ anti-leakage red line |
| `pittsburgh_val` ❌ not used | 60 val logs of split3 | val took part in checkpoint selection, so it is mild leakage for closed-loop diagnosis |
| `pittsburgh_test` ❌ not used | 60 test logs of split3 | R4-7 locked set, used only once after the method is frozen; must not be used for diagnosis |
| `boston` ⚠️ to be rebuilt | Cross-city held-out | `boston_clean/` has been lost; before re-running, `train_boston` must first be deep-screened in the same way |

## Reproduction commands

```bash
# 1. Rebuild the in-dist evaluation pool (CPU, seconds)
PYTHONPATH=/mnt/local/Xiao_Yi/nuplan-devkit \
  /home/team/anaconda3/envs/nuplan/bin/python \
  /mnt/local/Xiao_Yi/nuplan-devkit/GNN_Trans/scripts/eval_closed_loop/build_pittsburgh_heldout.py \
  --build --validate --limit 300 --workers 8

# 2. Queue until a GPU is free, then run the whole batch automatically (survives across sessions; do not kill with pkill -f)
SCENARIO_SET=pittsburgh_heldout \
GROUP=/mnt/local/Xiao_Yi/nuplan-devkit/GNN_Trans/experiments/closed_loop/pittsburgh_heldout_N20 \
setsid bash /mnt/local/Xiao_Yi/nuplan-devkit/GNN_Trans/scripts/eval_closed_loop/queue_pittsburgh_indist.sh &

# 3. Run a single cell manually
bash /mnt/local/Xiao_Yi/nuplan-devkit/GNN_Trans/scripts/eval_closed_loop/run_closed_loop.sh \
  --scenario-set pittsburgh_heldout --planner gnn_trans --mode nonreactive \
  --n 20 --device cuda --cuda 0 --group <group_dir>

# 4. Extract scores
/home/team/anaconda3/envs/nuplan/bin/python \
  /mnt/local/Xiao_Yi/nuplan-devkit/GNN_Trans/scripts/eval_closed_loop/extract_scores.py <group_dir>
```

## Verified

- `logs_pittsburgh_heldout.txt`: 960 entries, zero overlap with E1's 600 logs (hard assertion passed), **consistent with the 960 of Stage ⑧**;
- Deep screening: `clean=300`, `db_error=0`, **consistent with Stage ⑧'s "300 clean, deep_bad=0"**;
  in addition, 412 logs contain no challenge-type scenarios — this is normal filtering, not DB corruption, and the two are listed separately in the log;
- Hydra config resolution: `--cfg job --resolve` confirmed that `data_root` / `db_files` / `num_scenarios_per_type` /
  `planner.gnn_trans_planner.checkpoint_path` all resolve as expected;
- The checkpoint is identical to Boston-250's: `experiments/magnet_imitation_e1/seed2_gpu2/models/best_model_default.pth`.

## Scope

- This harness only evaluates; it does not train, does not change planner logic, and does not touch the danger line;
- The `pittsburgh_heldout` scenario distribution is dominated by high speed (Stage ⑧ measured `high_magnitude_speed` ≈ 63%),
  which differs in shape from the Boston pool → cross-scenario-set comparisons must also look at the per-`scenario_type` breakdown, not just the overall score;
- Pittsburgh has 14 types whereas Boston has only 13 (`traversing_pickup_dropoff` is naturally missing) →
  before comparing the overall scores of the two sets, restrict to the 13 common types; otherwise the equal-weight aggregation is not like-for-like.
